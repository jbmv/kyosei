# Rules and exit codes

The rules that have machinery behind them, and what each exit code means.

## Rules with machinery behind them

governs: src/kyosei/doctor.py, src/kyosei/doctor_consumers.py, src/kyosei/doctor_dispatch.py, src/kyosei/doctor_exports.py, src/kyosei/doctor_install.py, src/kyosei/doctor_records.py, src/kyosei/doctor_registry.py, src/kyosei/contracts.py

| Rule | Mechanism |
| --- | --- |
| Prose never travels as a shell argument | descriptions, notes and criteria have no flag-value form; single-line flags refuse newlines |
| Every write reports what it stored | each mutation echoes the text with its length and sha256 prefix |
| Ids are never reused or renumbered | a dedicated allocation table; nothing is ever deleted |
| Contracts hold at the transition | checked inside the write transaction; exit code 2 names the unmet item |
| Exports stay true to the database | `kyo doctor` re-derives every file and fails on mismatch |
| No finding grows with the store | every check is run against a large broken fixture and held to `doctor.MAX_FINDING_CHARS`; a name bound to a collection, interpolated whole into a message, is refused in the source (KYO-362) |
| No stored field without a consumer | `kyo doctor` compares the live schema against a registry of readers |
| Agents never type a time | no flag accepts a timestamp; all stamps are UTC ISO-8601 with `Z` |
| Kinds are validated, not free strings | `kyo new` refuses a kind absent from `kyosei/kinds.yml`, listing the known ones |
| Scopes are validated, not free strings | every write path refuses a scope absent from `kyosei/scopes.yml`, listing the declared ones; `kyo doctor` catches one that leaves the registry later |
| Statuses are per-project; contracts are not | every contract binds to the archetype **role** a status declares in `kyosei/statuses.yml`, so renaming `done` to `shipped` moves the label and nothing else; `kyo doctor` catches a record whose status has left the registry |
| Gate tags are validated, not free strings | `kyo gate --tag` and `kyo list --gate-tag` both refuse a tag absent from `kyosei/gate-tags.yml`, listing the declared ones; `kyo doctor` catches one that leaves the registry later |
| A gate is never a status | there is no `gated` status and no role for one; a record can be `working` and blocked, and `kyo list --gate-tag` selects on the gate dimension without touching the status one |
| A gate's tags are correctable without a false clearing | `kyo retag <gate-id>` (with `--tag NAME ...`, or `--no-tags` to carry none) UPDATEs `gates.tags_json` and nothing else — the gate's id, its `--do` payload and its created/cleared history are not in the statement, so retagging creates no gate and clears none, and it emits its own `retag` event rather than an unexplained export diff. Tags are replaced, not accumulated, and the previous set is echoed beside the stored one so a caller who meant "and this one" sees what they dropped. It refuses a tag absent from `kyosei/gate-tags.yml` before the transaction opens — through the same `_validated_tags()` call site `kyo gate --tag` uses, so the wording cannot drift into a second sentence — and it refuses an invocation giving neither `--tag` nor `--no-tags`, since an absent flag cannot mean both "clear them" and "you forgot it" |
| A scope is never derived from touches | the touches-based suggestion is printed labeled `derived`, has no write path, and `kyo rebuild` derives nothing |
| A document declaration is never derived from the repository | `kyo docs suggest` prints drafts labeled `suggestion only, nothing written` and has no write path; every block is run through the registry's own validator before it is offered, so a draft the next command would refuse is never printed. No `kyo doctor` PROBLEM reads one — the single NOTICE names the command and the count of drafts and reproduces nothing, and a question that drafts nothing (a numbered file whose history does not show it growing at its end, KYO-562) is not counted — and `docs_suggest_notice: false` in `kyosei/config.yml` turns that line off, because a suggestion that cannot be declined is not a suggestion (KYO-303) |
| A doctor finding never names a remedy that destroys the newer text | the asset checks (`skill`, `procedures_rules_missing`, `procedures_rules_differ`) compare against whichever copy is the *source* for the project running them: the packaged one for a consumer, and this checkout's `src/kyosei/defaults/` for the repository the package is built from, where `kyo install-skill`/`install-procedures` would write an older build's text over a newer edit. A build that merely lags is the `installed_build_lag` **notice**, whose remedy is reinstalling `kyo` (`uv tool upgrade kyosei` for a release, `make install-tool` for a snapshot of a checkout) and never an `install-*` command, and every remedy a finding does name is proved by a test to clear it without losing the newer text (KYO-309). KYO-318 adds the hook check to that list — it compared `.claude/settings.json` against the running build's fragments rather than the checkout's, so a hook group deleted from `src/kyosei/defaults/hooks/` read as one the project was missing — and closes the write side: `kyo install-skill`, `kyo install-procedures` and `kyo install-hooks` refuse, before writing anything, when this checkout is the source and the build's copy differs, each naming the direction and two remedies a test proves reach what was asked without losing the newer text |
| A saved view is not a second query | `kyo list` and `kyo base run` call one engine (`src/kyosei/query.py`); the filter set is one dataclass both surfaces derive from, and a test fails if either gains a filter the other lacks. The one named exception is `kyo list`'s own row-count flags, `--unsettled` and `--limit` (`query.LIST_ONLY_FLAGS`, which says why), and the test excludes exactly those |
| A saved view cannot ask what the registries do not license | `kyosei/bases.yml` is validated on load: an undeclared kind, status, scope or gate tag is refused in that registry's own words, an unknown column or sort key names the field set, and every problem in the file arrives at once |
| `kyosei.db` is always rebuildable | `kyo rebuild` reconstructs it from `kyosei/export/` alone; `kyo doctor` verifies the round trip |
| A committed event is never lost to the next rebuild | every command appends its ledger rows (event, sweep run, brief run, shift note) before any re-derivable artifact; `kyo doctor`'s `ledger_gaps` check compares each table's ids with its ledger's, and `kyo export --refresh` re-appends what an interrupted command left out (KYO-404) |
| A commit never re-stores the whole audit log | the events ledger is a directory of bounded shards (`kyosei/export/_events/`), appended to the newest one until it reaches 4 MiB — git stores a changed tracked file as a whole new object, so one file that only grows costs its entire size on every commit that touches it. The rule is stated once, in `events_ledger.shard_to_append_to`, and a test walks the module's AST to keep it there. An export still on the single `_events.jsonl` reads unchanged and `kyo doctor` reports it as a notice naming `kyo export --migrate-events` (KYO-268) |
| An event snapshot is bounded by its record, not by its evidence | `before`/`after` carry each evidence artifact as `{id, sha256}`; the body is stored once, on the record's own export document. Embedding it made one artifact a per-mutation copy — measured on a fixture record with a 1 MB artifact, the largest snapshot goes from 1,049,469 bytes to 741 (KYO-268) |
| Rebuild ids never reissue a retired one | id counters come from `_allocations.json`, never from `max(seq)` alone; each is seeded at the higher of the snapshot and the highest loaded id + 1, so neither a hand-deleted row nor a snapshot left below the ledger by two overlapping writers can reissue an id, and `kyo doctor` compares every scope, doc-refs and docs-obligations included, from the same list (KYO-414) |
| A store older than this build fails at open, not mid-command | `kyo` compares the db's own `meta.schema_version` (the authority) against this build before running any command |
| A schema change without a version bump fails the test suite | a normalised hash of the DDL is pinned to `schema_version` |
| `kyo rebuild` accepts any earlier shipped export format | a small, explicit per-version defaults table (`kyosei.schema.EXPORT_FIELD_DEFAULTS`) fills fields that format didn't write |
| A failed rebuild never leaves a partial `kyosei.db` | the partial file is removed before the error propagates |
| A criterion's state agrees with its latest verification | `kyo doctor` fails the build otherwise (law 3) |
| `kyo rebuild` leaves config.yml and the db agreeing on schema_version | rebuild rewrites `kyosei/config.yml` on success (KYO-5.c1) |
| Every error message naming a remedy has a test proving the remedy works | `tests/test_kyo5_error_remedies.py` runs the exact named command and asserts the error is gone |
| Two refusals about the same situation cannot drift apart | where two messages must tell one reader the same thing — that this build is behind the artifact in front of it, at the db boundary and at the export one — the shared clauses live in `contracts` and neither site states them. Two tests, because containment alone is not enough: one asserts both messages carry the clauses *as `contracts` renders them*, the other that neither source file states them literally, so a site that quietly went back to its own copy fails even while it still reads correctly (KYO-182) |
| Export drift from a format bump has an explicit, complete repair path | `kyo export --refresh` rewrites every drifted document; plain `kyo doctor` never auto-repairs |
| A format bump's own drift is reported once, not once per document | `kyo rebuild --force` names `kyo export --refresh` when the export it read is now behind the database it wrote; `kyo doctor`'s `exports`/`export_roundtrip` checks collapse a schema_version-only difference into one finding naming the count and the remedy, while a document differing any other way still gets its own (KYO-216) |
| A dispatch never renders as anything that reads like "done" without a report | `state` is always `running`/`reported`/`terminated-no-report`/`withdrawn`; `kyo doctor` checks reported⇒has-report, and that either report-less state implies a recorded why and no report_id |
| A dispatch that nobody ran is not recorded as one that died | `kyo dispatch close --withdrawn --why` is its own terminal state, listed in no brief and rendered under its own word; law 8's `terminated-no-report` keeps meaning that the work stopped, which is what makes flagging one worth doing (KYO-345) |
| A worker report is never retyped or hand-applied | `kyo report` validates and stores it structurally; verdicts reach criteria only through `kyo verify` |
| A dispatch never dispatches into another running dispatch's files | touch-disjointness checked before the brief is frozen; `--force` records the override on the dispatch |
| A split's successor and original stay linked both ways | `kyo doctor`'s `split_backlink_symmetry` check verifies the successor criterion and the `produced-by` link both exist |
| Sweep flags, never edits | `kyo sweep`'s four flag classes only ever `INSERT` into `flags`; no code path in it writes to `records`/`criteria` |
| A resolved flag's resolver and moment are recorded together, or not at all | `kyo doctor`'s `flag_resolution_consistency` check fails if `resolved_at`/`resolved_by` ever disagree |
| Every flag names a real flag class | `kyo doctor`'s `flag_types` check fails on anything outside `contracts.FLAG_TYPES` |
| Sweeping twice with nothing new creates no duplicate flags | each flag class checks for an unresolved flag with the same detail before inserting |
| A staleness flag does not outlive the record it was raised under | `kyo move` (into a completion status), `kyo wont-do` and `kyo void` all pass through `cmd_records._transition`, which closes that record's open `touch-changed`/`touch-missing`/`description-predates-claim` flags in the same transaction as the status write, naming the move and the actor; `near-duplicate-criteria`/`gate-cleared-stale-criteria` are left open on purpose; `kyo flag resolve --settled` repairs debt a store accumulated before this existed (KYO-346) |
| "What changed since the last brief" is never a git diff | `kyo brief` reads its own previous run's `last_event_seq`/`last_shift_note_seq` from `brief_runs`, a table, not `git log` |
| A shift note is surfaced exactly once | `kyo brief` advances its `shift_notes` cursor every run, even when the shift log is empty |
| Two dispatches never share a checkout by accident | `kyo dispatch` records the worktree the orchestrator declared with `--worktree` (defaulting to the project root, so undeclared dispatches collide) and refuses a second running dispatch into it; `--force` overrides, symmetric with touch-disjointness |
| The git-canonical store never gains a new absolute filesystem path | every path-typed column (`dispatches.worktree`, `touches.path`) is written through `contracts.store_path`, which stores the form relative to the project root — a sibling worktree as `../kyosei-wt-31`, the root itself as `.` — and the frozen brief states that same form; display resolves, storage does not. A directory touch stores that same relative form plus the trailing `/` that declares it one (KYO-209), which is why neither the project root nor a path resolving outside it may take that form; a new-file touch stores it with a leading `+` (KYO-225), which `contracts.touch_target` strips wherever a path is compared, so the marker says what the touch is without changing what it claims |
| A dispatch worktree never lands beside the user's other projects, and never survives forever | `kyo dispatch --branch NAME` derives `~/kyosei/<project>/dispatch worktrees/NAME` — the same home the store's own default uses, never a sibling of the code repository and never inside it (the arrangement git itself warns about); the space in that directory name is deliberate and is the whole of KYO-89, whose reasoning is written above `WORKTREES_DIRNAME` in `src/kyosei/config.py`: a worker's environment must be at least as hostile as the integration environment on every axis the worker cannot observe, and path spacing is the cheapest axis to invert; `kyo worktrees --prune` removes the ones whose dispatch has finished — only registered worktrees of this repository, each with `git worktree remove`, never another directory a dispatch recorded (KYO-402), and never a path a still-running dispatch also records, whatever the finished one's state (KYO-475) — and **refuses** any holding uncommitted work, because that directory may be the only surviving copy of a dead worker's output |
| A prune never removes the directory a rehearsal still has to run in | `kyo worktrees` states merged/unmerged per finished worktree, and `--prune` leaves any whose worktree HEAD is not contained in the base (or that git could not decide about) — the HEAD, not the declared branch, because a worker that committed on a detached HEAD never moved its branch (KYO-402), naming `--include-unmerged` on each line it holds back — "finished" means `reported`, which is true the instant the worker stops and says nothing about whether anybody merged it (KYO-207) |
| A worktree under that home records neither a username nor how deep the project sits | it stores as a `<worktrees>/<branch>` token resolved at read time, rather than the `../../../kyosei/<project>/…` chain KYO-52's repo-relative rule would otherwise produce; an explicitly-given `--worktree` still stores KYO-52's way |
| A dispatch says what executed it, and says so honestly | `worker_model` in `kyosei/config.yml`, overridable by a kind's `policy.worker_model` and by `kyo dispatch --model`, is recorded on the dispatch and stated in the frozen brief — with `enforced-by: aspirational` written verbatim in `procedures.md`, because Kyosei does not spawn workers and no `kyo` command can make a harness honour it. A dispatch that declares none records NULL and every surface says "not declared" |
| A worker is never told a fresh worktree holds tooling that is not there | `git worktree add` checks out tracked files and nothing else, so a `.venv/`, a `node_modules/`, a built binary or a seeded database is absent the instant a worker arrives — while the project's own README, CLAUDE.md and Makefile go on naming paths true only in a checkout somebody had already built in. `worktree_setup` in `kyosei/config.yml` is the project's declaration of what to run; `kyo dispatch` renders it into the frozen brief and prints it beside the line naming the worktree it created (KYO-485), and **runs none of it** — what a worktree needs is a fact only the consuming project holds, so the mechanism declares rather than assumes. A project that declares nothing gets a brief stating what a fresh worktree is *missing* rather than one that silently lacks it, and no surface ever asserts that a path exists (KYO-143). An entry may be a bare command or `{run: ..., note: ...}`, and the note is rendered as a `#` line under its command in the brief — a trailing YAML comment is not a value, so the caveat that `npm ci` exits 0 in two seconds while skipping install scripts reached nobody, three dispatches running (KYO-164) |
| A worker knows its environment crossed the boundary its files did not | a worktree isolates *files* and inherits the spawning process's *environment* unchanged, so `VIRTUAL_ENV` and `PATH` can still point into the orchestrator's checkout — measured in KYO-143's own dispatch worktree, where the orchestrator's `.venv/bin` led the inherited `PATH` and bare `python`/`pytest`/`kyo` all resolved to the orchestrator's interpreter importing the orchestrator's source. The failure runs backwards as readily as forwards: an installer honouring the inherited `VIRTUAL_ENV` points the *orchestrator's* venv at an unmerged worktree's source, and both sides report success. No declared setup command can fix it, so every brief naming a worktree says so regardless of what the project declared |
| A record's declared touches are checked against what its branch actually changed | `kyo report` and `kyo touch-drift` compare the claim to the same three-dot diff `kyo check-branch` computes and name the files edited outside it, with the exact lines `kyo edit --touches-file` would need. It **reports and never refuses**: a touches table is a prediction, and the branch that edits outside its claim is usually the branch that was right |
| A path pasted into stored *prose* is at least said out loud | prose is not path-typed and cannot be fixed by a column rule, so `kyo` warns (never refuses) when text entering the store names a home-directory-shaped absolute path, in both human and `--json` output |
| Every verbatim-prose store is redactable, not just evidence | `contracts.REDACTABLE` lists all four (evidence, claim, note, shift note); `kyo redact` dispatches on the id's own shape and `kyo doctor` iterates the same table, so a prose store added to the schema without being added there shows up as an untested kind |
| Redacted evidence is redacted everywhere, not just in the db | `kyo redact` rewrites the artifact **and** scrubs the events ledger, where every mutation of that record had been copying the text until KYO-268 reduced an event's evidence to `{id, sha256}` — older lines still carry it, so the scrub still runs; the db's `events` snapshots are scrubbed in the same transaction, and `kyo doctor`'s `redactions` check fails a half-applied one — reading the row, the ledger and the events table, and naming the same-reason `kyo redact` rerun that finishes it (KYO-405); a record's title, description or criterion redacted by id is checked the same way, up to its own redaction event, and `tests/test_redact.py` fails if either the target or the check is removed (KYO-426) |
| An agent never publishes the maintainer's private thinking by pushing | `kyo check-push --pre-tool-use` fails (exit 2) on a `git push` into a repository that carries an unacknowledged store, stating counts it measured at that moment; wired into `PreToolUse`. Since KYO-409 the repository judged is the one the push's own directory belongs to (the payload's cwd, a `cd` ahead of it, `git -C`), not the hook's; the command word is read past env prefixes and the wrappers `env`, `command`, `nohup`, `time`, `timeout N`, `nice`, `exec`, a single `&` separates, and `( … )` is unwrapped — one parse, `kyosei.shell_words`, shared with `kyo check-command`. A Bash call that is not a push returns before anything is measured. A directory it cannot follow (variables, `cd -`, `git --git-dir`) is never blocked; shell keywords, `$( … )` bodies, `sudo`, `bash -c` and scripts are not read. The human half is a git `pre-push` hook that warns and does not block, because a human pushing their own repository owns that call |
| That warning fires once, not every time | acknowledging records who and when in `kyosei/config.yml` under `publication_acknowledged`, and `kyo rebuild` carries it forward rather than rewriting it away |
| A worker branch never diffs the structured store or the ideas layer | `kyo check-branch [--against <ref>]` fails (exit 2) on anything under `kyosei/` or `ideas/`, and on a branch that adds, deletes or changes the `.kyosei` store link (an exact path, `contracts.GUARDED_BRANCH_FILES`, KYO-403); wired into the `SubagentStop` hook, whose `--against main` is a spelling for this repository's trunk: `trunk` in `kyosei/config.yml` when declared, else `origin/HEAD`, `init.defaultBranch`, `main`, `master`, and a declared trunk naming no ref is refused by the key's name (KYO-410) |
| A worker never picks a numbered section's number | for a document a project declares `numbered:` in `kyosei/documents.yml`, the number depends on every other branch in the wave, and the branches that would have to agree cannot see each other. So workers write per-dispatch fragment files under a declared directory (a path no other dispatch can write) and `kyo check-branch` fails (exit 2) on a branch that ADDS a numbered heading to the document itself, naming the fragment path instead. Editing an existing section is not refused. `kyo docs assemble` assigns the numbers on the merged tree, refuses the whole run rather than assembling half of one, and NAMES the project's own index command without running it (KYO-299) |
| A worker never runs the whole suite inside its own worktree | `controller_only_commands` in `kyosei/config.yml` declares which command lines ARE the suite — because only the project knows — and `kyo check-command --pre-tool-use` fails (exit 2) when one of them would run inside the declared worktree of a dispatch whose state is `running`, by the payload's cwd or by the `cd`s in the command line. Matching is on tokens from the command word, read past any env prefix, redirections and the wrappers `env`, `command`, `nohup`, `time`, `timeout N`, `nice`, `exec` (KYO-409, the parse `kyosei.shell_words` shared with `kyo check-push`), with a single `&` a separator and `( … )` unwrapped, so `make test LOG=...` and the `nohup make test > log 2>&1 &` form the timeout refusal recommends match while `make test-data` and `echo "make test"` do not; a declared `make` command matches on make's targets past its options, so `make -j4 test` does. The directory follows `cd`, `pushd`/`popd`, `env -C` and `make -C`; what it will not parse (`cd -`, variables, substitutions, `git -C`) leaves the directory *unknown*, and unknown never refuses; shell keywords, `$( … )` bodies, `sudo`, `bash -c` and scripts are not read. A project that declares nothing is refused nothing and opens no database. The override is one word, `KYOSEI_SUITE_OK=1` in front of the command, named in the refusal and asked to be reported as a disagreement — because contradicting a rule must cost less than complying with one that is wrong. Prose alone had already failed here: the rule was in every brief of one measured wave and lost to the same brief's `worktree_setup` (KYO-298) |
| The rule and the config that contradicts it are not both left standing | `kyo doctor`'s `orchestrator_only_setup` check is a **notice** for every `worktree_setup` entry that is itself a declared orchestrator-only command, naming both config lines. A notice rather than a failure because which of the two lines is wrong is an editorial judgment about the consumer's own project; both the check and the guard call one matcher (`cmd_check_command.controller_only_matches`), so the notice cannot say a config is fine while the guard goes on refusing its workers (KYO-298). The same check notices the key declared under its pre-KYO-519 spelling, `controller_only_commands`, naming the hand rename and its precondition (every `kyo` reading the store at least KYO-519, or an older one refuses the new spelling `orchestrator_only_commands` and every hook goes blind) (KYO-519) |
| Whether that policy is working is measured, not asserted | `context_rewrites`/`context_rewrite_tokens` on every dispatch's token answer — an assistant message after the first whose cache creation was over 50,000 tokens and at least 80% of its whole context, counted once per message id, which is what the harness's prompt cache expiring under a long foreground command looks like. Read off `kyo show <dispatch-id>` and `kyo worktrees --json` in any project, rather than from the ad-hoc script that measured the two re-writes this policy is justified by (KYO-298) |
| A worker never waits out a long run in one foreground command | `worker_command_timeout_ceiling_seconds` in `kyosei/config.yml` states the longest timeout a Bash call may DECLARE inside a running dispatch's worktree, and `kyo check-command --pre-tool-use` fails (exit 2) on one that declares more — the `PreToolUse` payload carries the tool's own `timeout`, so the intent is legible at the only moment refusing it saves anything. A call that declares none runs under the harness default and is never refused. Separately opt-in from `controller_only_commands` and with no default, because the cost exists only while the consumer's prompt cache is shorter than the wait; the override is one word, `KYOSEI_LONG_OK=1`, reported as a disagreement. Prose alone had already failed here too: the rule was in the brief of the worker that waited 10.1 and 6.1 minutes in single `until ...; do sleep 30; done` loops for 250,466 and 255,899 tokens of re-write, and the rule's own "look once" advice was half the reason (KYO-312) |
| A project's hooks never fall silently behind the build | `kyo doctor`'s `hook_config` check compares `.claude/settings.json` against the packaged templates and names `kyo install-hooks` as the remedy; comparison is per `&&`-separated command, so extending a hook is not mistaken for missing it. A hook that is exactly a line an earlier build installed is the `hook_config_superseded` **notice** instead, so an upgrade does not fail the `Stop` hook; a missing hook, or a Kyosei command matching no packaged text, stays a problem (KYO-604). A project on the plugin has no copied hooks to compare, and reads one `harness` item in their place: present, missing, behind, copied or doubled, each with its fix (KYO-596) |
| A consumer gets the workflow, not just the enforcement | Kyosei's Claude Code plugin carries the packaged `/kyosei` skill and loads it from the installed build (KYO-593). On the copies, `kyo install-skill` (also run by `kyo install-hooks`) writes it into the project, plus the marked Kyosei section in its CLAUDE.md that names it to a session where no session-start hook runs (KYO-508; the skill itself loads when the session-start brief names a Kyosei project), and `kyo doctor`'s `skill` check reports a copy, or a CLAUDE.md section, that has drifted from the build it documents — the third instance of "we ship code that updates itself and copies that never do". `kyo install-skill` ends each file with the digest of the text it wrote, and a copy that still matches its digest is an earlier build's unedited skill, the `skill_superseded` **notice**; an edited copy, or one with no digest, stays a problem (KYO-604) |
| The workflow an orchestrator re-reads every turn is not mostly history | the skill is two tiers (KYO-328). `.claude/skills/kyosei/SKILL.md` is the workflow — each instruction, at most a clause of reason, and the record id that carries the story — and `.claude/skills/kyosei/REFERENCE.md` beside it holds the incidents, cited by section at the end of every section and read on demand. It was 54,823 bytes loaded whole into every session and re-read every turn; the workflow tier is now 27,399, under a ceiling `tests/test_skill_cli_sync.py` enforces so it cannot creep back. `kyo install-skill` writes both files, `kyo doctor`'s `skill` check compares both, and a project holding one without the other is reported — a workflow whose every pointer is dead is KYO-149's defect from the other side |
| A rule added to the packaged default reaches a project that already has a store | `kyo doctor`'s `procedures_rules_missing` check compares `kyosei/procedures.md` against the build's packaged default rule by rule and names `kyo install-procedures` for each rule the project lacks; that command **merges** — it inserts the missing rules in packaged order and leaves every other byte alone, because the ledger is project-editable by design and overwriting would delete rules a consumer wrote on purpose. A rule whose text the two copies word differently is `procedures_rules_differ`'s business instead, and that one is a **notice** (`doctor.NOTICE_CHECKS`, KYO-214): reported with both sides quoted on every run, and never a failure, because the packaged copy ships inside the installed package and a deliberate rewording is a legitimate state. Nothing rewrites it *silently* — `kyo install-procedures` still never touches a rule already there on its own, except one whose text is exactly a wording an earlier build shipped for it (`procedures.SUPERSEDED_RULE_WORDINGS`, held to the packaged default's git history by `tests/test_kyo_procedures_unedited.py`), which nobody in the project wrote and which the plain run moves to the packaged wording, printing both texts, while that check names the plain rerun rather than `--adopt` for it (KYO-515) — but `--adopt "<rule title>"`/`--adopt-preamble` are the opt-in override the notice names beside the rule: on request, they replace the store copy's text with the packaged wording, refusing a rule the packaged default does not ship or one already identical (KYO-151.c2). A rule only the project carries is reported by neither. The one comparison behind both checks, the command and this repo's own `tests/test_procedures.py` lives in `kyosei/procedures.py`, so they cannot disagree about what a difference is (KYO-212) |
| A grant added to the packaged kind registry reaches a project that already has a store | no command merges `kyosei/kinds.yml`, so `kyo doctor`'s `kind_grants_missing` **notice** compares each kind's `accepts_from` with the packaged default's (this checkout's `src/kyosei/defaults/kinds.yml` in the repository the package is built from, KYO-309) and names every entry the project lacks, the command it refuses (`kyo new`, `kyo promote`, `kyo spawn`) and the exact line to write — plus the other kind's `produces` line when the grant names a kind, which the loader requires. `accepts_from` only; a kind only one side defines is not compared. A notice, not a failure, because a kind narrowed on purpose is a legitimate registry, and `kind_grants_notice: false` in `kyosei/config.yml` declines it for every kind; a test proves the printed edit clears it (KYO-394) |
| A policy key added to the packaged kind registry reaches a project that already has a store | `kyo doctor`'s `kind_policy_missing` **notice** compares each `knowledge` kind's `policy` with the packaged default's and names every key the project's `kyosei/kinds.yml` does not set (`raises_docs_obligations` on `decision`, KYO-554, is the first), with the exact line to add under the kind's `policy:`. Only absent keys: a key the project states, even as `false`, is its answer. A notice, not a failure; `kind_policy_notice: false` in `kyosei/config.yml` declines it, and a test proves the printed line clears it. When the session-start brief prints BUILD CHANGED it prints this notice and `kind_grants_missing`'s under it, so an upgrade says what it asks of an existing store without anyone running `kyo doctor` (KYO-556) |
| The board a human reads is never behind the store | it has no copy to be behind. `kyo html` regenerated a static site and `kyo doctor`'s `html_freshness` check told you when it had gone stale; KYO-215 retired both, because a viewer that must be re-run to stay true is a viewer that is wrong between runs, and the stop hook that re-ran it made every session end in HTML churn no commit carried. The desktop app reads the store live, and `kyo show`/`kyo list`/`kyo map`/`kyo brief` read it directly. `kyo doctor`'s `retired_html_directory` notice tells a project that still has the old `kyosei/html/` on disk, once, that nothing writes it any more |
| A plan renders the one thing it is for | `kyo list --plan` and a members block with its status distribution in `kyo show` — derived at display time, never written into the export, so a member's `--plan` edit cannot stale the plan's own document |
| A plan cannot close over open members without saying so | `kyo move <plan> <a completion status>` prints the member distribution and refuses by name (naming both remedies) when any member is unsettled; `--force` overrides it and writes a record note naming the members it closed over (KYO-308) |
| A record does not settle past an open gate | `check_transition`'s `settled-requires-no-open-gates` refuses `kyo move` into a completion or retired status, `kyo wont-do` and `kyo void` over any open gate, naming each gate and `kyo ungate <gate-id> --why`; `kyo accept --close` reads the same refusal and leaves the record open; `--force` settles anyway, leaves the gate open and lists it (KYO-490) |
| A record is not called verified before a verdict is recorded | `check_transition`'s `verified-requires-a-verdict` refuses `kyo move` into the `verified` role while any live criterion of a `requires_criteria` kind has no verification row at all, naming each such criterion, `kyo verify <cid> --verdict <verdict> --method <how>`, and `kyo accept <dispatch-id>` for any ingested report holding an unapplied verdict for it; the `needs-verification` role is untouched, since entering it is how verdicts get asked for (KYO-546) |
| A rule can reach every audience that needs it | `audience: worker, orchestrator` parses as two (`controller`, the pre-KYO-519 spelling, is read as `orchestrator`, and the packaged ledger says `orchestrator` since KYO-524); `kyo doctor`'s `procedures` check fails an audience token nothing selects on, because a rule reaching nobody looks exactly like one that reaches someone |
| A worker never stops on uncommitted work, and is never asked to commit the orchestrator's | `kyo check-clean` fails (exit 2) on a dirty worktree, excluding the directories `check-branch` forbids — both read `contracts.GUARDED_BRANCH_DIRS`, so the two halves of `SubagentStop` cannot contradict each other |
| A stop by an agent that was never a worker is neither checked nor counted as an unmatched worker stop | `resolve_stop_target` classifies a `SubagentStop` whose agent has no transcript, no spawn sidecar and no sidechain row — in a session whose `subagents/` directory does hold other agents' transcripts — as `no-transcript-not-a-dispatched-worker`, and both guards return before running git anywhere, where they used to fall back to the orchestrator's own cwd. The stop is still counted — in place, on each running candidate dispatch's own row (KYO-375), and an `unresolved` stop the same way with its reason since KYO-418, so neither grows the events ledger and a tick never rewrites a finished dispatch's record; `kyo worktrees` prints the ledger's sentence on one line, and `kyo worktrees --expand-stops` adds one line per named dispatch with its unmatched stops by reason and then the per-stop lines (KYO-423; `--json` carries every stop either way) and `kyo doctor` prints the matched / unmatched-worker / not-a-worker census on the `unresolved_stops` line. Measured before it: 6,277 of 6,284 unmatched stops were such agents — the ~32s `SubagentStop` tick (KYO-163) — and the section listing them was 12,791 lines. A session with no agent transcript at all is left `unresolved`, because there an absent file cannot be told from a harness that moved its files (KYO-373) |
| A worker commits its work without committing its report | one named path (`contracts.WORKER_REPORT_PATH`) stated by every brief, written into the code repository's `.gitignore` by `kyo init` and `kyo install-hooks`, excluded by `kyo check-clean` and never named by `kyo touch-drift` — while `kyo report --file` still reads it |
| An informational finding never fails the hook it is printed from | `kyo doctor` has two tiers and a check declares its own — membership in `doctor.NOTICE_CHECKS`, beside the `CHECKS` registry. Exit 3 answers to the problem tier alone; notices print in full under their own heading and exit 0. Claude Code renders any hook exiting nonzero as an error block, so a finding that says of itself "this is not a block and never was" (`unresolved_stops`) was rendering as a hook error on every stop of every dispatch until it declared its tier |
| A hook that checked nothing says so, and the build that will blind every hook is named before it does | every hook a project installs runs the `kyo` on **PATH**, which is a different program from the one an orchestrator edits the store with — so a config key or a `schema_version` the PATH build does not know makes `ctx.store()` raise inside every hook at once. In one measured incident every hook in a project was blind for two hours: no stop audited, no brief injected, and the two `SubagentStop` guards reporting on the orchestrator's checkout while three workers' trees went unexamined — each hook's exit saying only that it had failed (KYO-325, KYO-335). A hook-shaped invocation whose store cannot be read now prints **NOTHING WAS CHECKED** on the first line of stderr: decided once at `cli.main`'s catch so it covers every hook rather than the one that was noticed, established by re-asking the store rather than by trusting the exception, and exiting non-blocking by force — exit 2 on `PreToolUse` would refuse every Bash call in the project, and nobody could then run the fix (KYO-316's measurement). `kyo check-command` says it where it deliberately swallows the refusal, instead of reporting that the project declares nothing when it could not read what the project declares. The condition is also caught *before* that window opens: `kyo doctor`'s `path_build_lag` check and `kyo rebuild` ask the PATH build the one question it cannot get wrong — `kyo where --json`, which exits 0 either way and carries its own refusal verbatim — and report that build's own words, that build's own upgrade route (never this one's), and what it costs. Both are silent when PATH's `kyo` is the program already running, so a hook can never go red over this |
| A criterion waiting on a person is never a wait only one session knows about | `kyo verify --verdict unmet-unobserved` prints the exact `kyo gate <id> awaiting:human-run --do "..."` line that would make the wait findable, quoting the criterion id and the reason just stored, and writes no gate — composing an instruction addressed to a person stays the orchestrator's act. `kyo brief`/`kyo next` carry the class as its own section and `kyo doctor` warns for each record in it, all four reading one predicate (`cmd_next.ungated_unobserved`), so they cannot disagree about which records are in it. The state is exact — an `unmet-unobserved` criterion, no running dispatch, no open `awaiting:*` gate — because while a worker is still out there that verdict is the honest state of something they are about to observe. The doctor check is a **notice** and is the first one to name a remedy command: the bar in `doctor.NOTICE_CHECKS` says those stay problems, and the exception is argued on the check itself — the condition is one the tool expects to see, so exit 3 would paint every `Stop` between the verdict and the gate red (KYO-267) |
| A `governs:` doc target that no longer exists fails the build | `kyo docs check` resolves every document section's `governs:` targets the same way a record's `touches` are resolved |
| The validator can see the files that actually went stale | which files are documents is `kyosei/documents.yml`'s declaration, defaulting to root-level `*.md` plus `docs/**/*.md` — a project with no `docs/` directory is scanned for its README rather than for nothing, and globs matching no file report `no-documents` instead of "clean" |
| A report cannot informally bundle a record its dispatch never declared covering | `kyo report` only accepts `criteria_verdicts` for the dispatch's own record or a record named in `--also-covers` at dispatch time |
| The `/kyosei` skill can never drift ahead of or behind the real CLI | `tests/test_skill_cli_sync.py` validates every named `kyo` invocation against the live argparse tree |
| Installing hooks twice changes nothing the second time | `kyo install-hooks` merges by `(event, type, command)`, skipping a hook group already present |
